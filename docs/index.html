Hack Hydra 2026 · Memory & Context Retrieval

Graph memory that shows its work.

Engram is agent memory on HydraDB that recalls the version of a fact that's true now, proves where it came from, and abstains when the answer isn't in the history — the things vector search structurally can't do.

The problem

Similar isn't current.

When a user updates a fact across sessions — a new personal best, a move to a new city — vector search returns the old value and the new one by similarity, with no way to tell which is true now. And it never abstains, so it confidently answers questions the history never covered. Memory has to track how a fact changed, and show why it recalled what it did.

How it works

A temporal provenance graph, on HydraDB.

Every history becomes a graph HydraDB traverses. Answers are graph walks, not similarity lookups.

1

Ingest

Sessions → messages → facts → entities. Each fact that updates an earlier one gets a SUPERSEDES edge. Written with batched UNWIND upserts.

2

Traverse

A typed multi-hop MATCH over STATES / ABOUT / SUPERSEDES plus HydraDB's native algo.SSpaths, filtered to the current fact.

3

Answer + receipt

Answer strictly from that evidence, with a receipt — the source message and the value it superseded — or abstain when nothing supports it.

Benchmark

Competitive on accuracy, alone on auditability.

LongMemEval-S, same model for both systems, LLM-judged. Accuracy is close; what only Engram provides is a receipt per fact and evidence-backed abstention.

CategoryEngram (graph)Vector-RAG

Honest read: the two are close on this small sample. Engram's edge is the provenance receipt and the refusal to guess — neither of which a vector retriever can produce. Temporal date-arithmetic is its named weak spot.
